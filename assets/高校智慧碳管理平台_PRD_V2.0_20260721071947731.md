# 1. 项目背景与机会

## 1.1 课题背景

本项目隶属"数智能碳课题组"，课题目标为：

- 面向北京市重点碳排放单位中的**医院和学校**，研究覆盖**数据采集→数据质量管理→碳排放核算→排放分析→减排路径→碳管理→碳资产管理→监督考核→示范创建**的全链条服务体系。
- 完成一套行业化解决方案、一份汇报材料和一个**轻量可演示的系统**。
- 利用虚拟样例数据展示核心指标、建设成效和领导驾驶舱效果。

**一期聚焦高校场景**，医院为后续扩展。采用虚拟高校客户，使用模拟数据，三周完成 Demo 开发。

## 1.2 产品定位

高校智慧碳管理平台**不是**通用"碳计算器"，而是一套以真实高校为客户原型、覆盖**数据采集→质量控制→核算报告→核查整改→配额履约→减排项目→监督评价**全过程的碳管理数字化平台。

它连接计量、账单、资产、建筑和组织数据，以可追溯核算为基础，向后勤提供异常处置，向碳管理员提供合规履约，向领导提供目标与决策信息，向监督评价提供证据材料。

## 1.3 业务目标与价值主张

### 北极星目标

> **让校方在任意时点回答四个问题：数据是否可信？排放从哪里来？年底是否会超配额？优先做什么项目最划算？**

### 业务目标（OKR 框架）

| Objective | Key Result | 量化目标 | 验证方式 |
|---|---|---|---|
| 让排放数据可见、可信 | 所有核算结果可追溯到活动数据、因子版本和支撑材料 | 抽样追溯成功率 100% | 随机抽样追溯测试 |
| 让管理流程闭环可控 | 每个重大异常可转为整改/减排项目并跟踪成效 | 闭环状态链覆盖率 ≥ 95% | 闭环流程演示验证 |
| 让履约决策有据可依 | 按情景预测配额缺口和资金敞口，展示关键日期 | 情景预测偏差 ≤ 15%（模拟数据校验） | 资产页面测试 |
| 让领导快速掌握全局 | 领导 3 分钟掌握总量、强度、目标、风险与重点问题 | 驾驶舱任务测试 ≤ 3 分钟 | 驾驶舱任务测试 |

### 课题交付目标

| 交付物 | 说明 |
|---|---|
| 行业化解决方案 | 覆盖背景、需求、行业场景、数据、核算、减排路径、碳管理、碳资产、监督考核、示范创建、系统和应用价值 |
| 汇报 PPT | 突出痛点、全链条方案、高校差异、领导驾驶舱、减排路径、价值 |
| 轻量可演示系统 | 可展示可交互的 Demo，覆盖主故事线 |

## 1.4 现状痛点分析

北京市重点碳排放单位承担月度数据、年度排放报告、第三方核查、配额管理与清缴等责任。高校同时具有多校区、多建筑、多能源、多业务场景和寒暑假波动等特征，单纯依靠账单和 Excel 难以形成稳定、可审计的数据链。

| 痛点 | 典型表现 | 业务后果 |
|---|---|---|
| 数据分散 | 后勤、财务、物业、供能单位各自留存表计、账单和合同 | 口径不一、重复填报 |
| 边界复杂 | 校区、家属区、出租商户、校办企业、共用设施边界模糊 | 漏算、重算、核查争议 |
| 质量滞后 | 年末集中补数，缺失和突变无人闭环 | 报告返工、履约风险 |
| 分析失真 | 未考虑建筑类型、面积、人数、气象和校历 | 难以判断"高耗能"是否异常 |
| 项目脱节 | 节能改造立项与排放台账、财务收益分离 | 减排成效无法证明 |
| 资产被动 | 只在清缴前核对配额和排放 | 采购时点与资金安排被动 |

## 1.5 政策事实基线（产品配置依据）

- 2026 年北京市重点碳排放单位须在每月结束后 **20 个自然日**内上报月度数据及支撑材料。
- 2026 年 **3 月 31 日**前报送上一年度碳排放报告，**4 月 30 日**前报送经核查排放报告和第三方核查报告。
- 2026 年 **7 月 31 日**前完成排放量确认和免费配额核定发放；**9 月 30 日**前提交抵销申请；**10 月 31 日**前完成清缴。
- 数据原始记录和管理台账等材料至少保存 **5 年**；重点单位应制定、报告并实施数据质量控制方案。
- 低碳校园评价关注碳排放强度、低碳管理、低碳文化和低碳运行，并要求重点高校按时报送、核查和履约。

> ⚠️ 上述日期是 2026 年度配置样例。产品必须提供政策日历后台，支持年度更新和有效期管理。所有排放因子、配额、价格及政策期限均须按年度配置，禁止硬编码。

## 1.6 为什么现在做

- 北京市碳市场持续收紧，高校作为重点排放单位的合规压力逐年增加。
- "双碳"战略下，公共机构节能降碳成为政策抓手，低碳校园评价标准已发布。
- 课题组需要在三周内产出可演示成果，为后续正式项目打下基础。

# 2. 需求概述

## 2.1 用户痛点总结

1. **看不到**：排放数据分散在多个系统和人员手中，领导无法实时掌握全局。
2. **算不准**：核算口径不统一、因子版本混乱、数据质量无法保证。
3. **管不住**：异常发现滞后、责任不清、整改无闭环。
4. **报不出**：年底集中整理数据，报告质量差、核查问题多。
5. **履约被动**：不清楚配额缺口、无法提前规划资金和交易策略。
6. **评不了**：低碳校园自评缺乏数据支撑和材料归集。

## 2.2 预期收益

| 维度 | 预期收益 | 量化指标 |
|---|---|---|
| 管理效率 | 从"年底突击"变为"日常管控" | 数据完整率 ≥ 98% |
| 合规保障 | 关键节点按时完成 | 报告/核查/清缴按时率 100% |
| 节能减排 | 异常可定位、减排可量化 | 异常关闭率 ≥ 90% |
| 决策支撑 | 领导 3 分钟掌握全局 | 驾驶舱任务测试 ≤ 3 分钟 |
| 资产优化 | 提前预警配额缺口 | 提前 ≥ 90 天预警 |

## 2.3 版本范围

- **本版本（V2.0 / MVP）**：三周 Demo，聚焦高校场景，5 个核心页面，虚拟数据驱动。
- **V2.0 不含**：真实设备对接、政府平台自动申报、交易所下单、移动端完整功能、等保测评。

# 3. 用户需求与功能需求

## 3.1 用户角色定义

**User Story**：作为分管副校长，我希望在打开系统后 3 分钟内看到年度排放总量、同比变化、目标完成情况和风险等级，以便判断是否需要关注或采取行动。

**User Story**：作为能源管理员，我希望系统能自动识别异常用能并告诉我哪栋建筑、什么时间段出了问题，以便快速定位原因并安排整改。

**User Story**：作为碳管理员，我希望核算过程中每一步都能追溯到原始数据和因子版本，以便应对第三方核查并确保数据可审计。

**User Story**：作为数据填报员，我希望有明确的填报模板和校验提示，以便减少错误并快速完成月度数据上报。

**User Story**：作为核查员，我希望在线查阅核算报告及支撑材料并提出不符合项，以便减少现场沟通成本。

## 3.2 关键职责分离

- 填报人与复核人不得为同一操作身份。
- 因子发布需碳管理员复核。
- 年度核算锁定后修改必须走解锁审批并保留前后版本。
- 配额交易仅记录与模拟，不直接执行真实交易。

# 4. 业务流程

## 4.1 端到端业务闭环

| 阶段 | 输入 | 系统动作 | 输出/状态 |
|---|---|---|---|
| 1 主数据准备 | 组织、校区、建筑、设施、表计、责任人 | 边界校验、有效期管理 | 可核算边界 |
| 2 数据采集 | 接口读数、账单、手工表、光伏数据 | 落原始区、去重、单位换算 | 待校验数据 |
| 3 质量控制 | 规则、历史、校历、气象、账单总量 | 完整性/合理性/一致性检查 | 通过、警告、阻断 |
| 4 碳核算 | 合格活动数据、因子、方法版本 | 按排放源计算并汇总 | 月度/年度排放清单 |
| 5 报告核查 | 报告模板、支撑材料、核查问题 | 生成、锁定、问题整改 | 报告版本、核查结论 |
| 6 分析预警 | 实绩、预算、目标、基线、校历 | 趋势、对标、预测、告警 | 问题清单 |
| 7 减排项目 | 异常、措施库、成本参数 | 方案测算、审批、MRV | 项目台账与实绩 |
| 8 碳资产 | 确认排放、配额、抵销量、价格情景 | 缺口/盈余和资金敞口预测 | 履约方案与清缴台账 |
| 9 监督评价 | 目标、任务、证明材料、评分规则 | 自评、差距、整改闭环 | 考核包/创建材料 |

### 四条核心闭环

1. **数据闭环**：数据异常 → 责任工单 → 复核关闭
2. **履约闭环**：排放预测 → 配额缺口 → 履约方案 → 清缴归档
3. **减排闭环**：异常/目标差距 → 减排项目 → MRV → 效益复盘
4. **评价闭环**：评价失分 → 整改任务 → 证据上传 → 重新自评

## 4.2 核心状态流转

### 活动数据状态
```
草稿 → 已提交 → 已复核 → 已锁定
                      ↑
            （回退须填写原因）
```

### 核算批次状态
```
试算 → 复核中 → 已锁定 → 经核查 → 已确认
                  ↑
       （解锁需申请审批，不覆盖原版本）
```

### 质量问题/工单状态
```
待确认 → 已分派 → 处理中 → 待复核 → 已关闭 / 误报
```

### 项目状态
```
建议 → 论证 → 已批准 → 实施中 → 已验收 → 运行评估 → 归档
```

### 报告版本状态
```
草稿 → 复核中 → 已锁定 → 经核查 → 已确认
```

## 4.3 正常流程示例：月度数据上报

1. 每月结束后 20 个自然日内，数据填报员导入/填报当月能耗数据。
2. 系统自动执行质量规则校验（完整性、合理性、一致性）。
3. 校验通过的数据进入"已复核"状态；校验不通过的生成异常工单。
4. 能源管理员处理异常工单，补充材料或修正数据。
5. 碳管理员确认数据质量达标后，执行核算计算。
6. 核算结果复核无误后锁定，生成月度排放清单。

## 4.4 异常流程处理

| 异常场景 | 处理方式 |
|---|---|
| 账单与表计差异超阈值 | 进入"待解释"状态，责任人补充说明 |
| 数据缺失超过容忍度 | 阻断锁定，要求补录或标记估算方法 |
| 绿电凭证量不足 | 回退至适用电力因子并告警 |
| 因子版本变更 | 不静默重算历史；用户选择"沿用"或"生成重算版本" |
| 已锁定周期需修改 | 走解锁审批流程，保留前后版本 |
| 阻断级质量问题存在 | 禁止锁定，列出问题清单 |

## 6.2 核算边界与方法

### 组织与运营边界

- 默认采用法人边界：纳入某大学在北京市行政区域内控制运营的固定设施。
- 按"学校—校区—建筑—区域—设施—计量点"建立空间层级。
- 出租、家属区、校办企业和共用能源站标注纳入/排除及分摊规则。
- 边界变化须记录生效日期、依据材料和对基准/配额的影响。

### 一期排放源

| 类别 | 活动数据 | 典型来源 | 一期处理 |
|---|---|---|---|
| 固定燃烧 | 天然气等燃料消耗量 | 燃气表、账单 | 活动量×低位热值×单位热值含碳量×氧化率×44/12 |
| 外购电力 | 购入/使用电量、绿电凭证 | 电表、账单、交易凭证 | 火电与绿电分开；因子按年度版本配置 |
| 外购热力 | 购热量 | 热量表、结算单 | 购热量×适用热力排放因子 |
| 光伏 | 发电、上网、自用量 | 逆变器/结算单 | 作为能源结构与减排贡献展示，不与购电重复扣减 |
| 其他 | 水、车辆、废弃物等 | 台账 | P1 扩展指标，不计入一期履约核心结果 |

### 核算规则

- **基础公式**：排放量 E = Σ(活动水平 AD × 排放因子 EF × 必要换算系数)
- 系统同时保存输入值、单位、换算过程、参数来源、参数有效期、公式版本、计算时间和计算人/任务。
- 同一计量周期只允许一个生效数据版本；账单与表计差异超过阈值进入待解释状态。
- 缺失值可临时估算，但必须标记估算方法、置信等级和替换期限。
- 绿电"零排放"仅在满足当年政策与凭证要求时适用。
- 因子变更不得静默重算历史。
- 预测排放不进入正式报告。

## 6.3 核心指标字典

| 指标 | 定义/公式 | 刷新 | 单位 |
|---|---|---|---|
| 碳排放总量 | 固定燃烧+外购电力+外购热力等纳入边界排放 | 日/月 | tCO₂ |
| 单位面积排放 | 排放总量÷纳入边界建筑面积 | 月/年 | kgCO₂/m² |
| 人均排放 | 排放总量÷折算用能人数 | 月/年 | tCO₂/人 |
| 同比/环比 | （本期-对比期）÷对比期 | 月 | % |
| 目标完成率 | 累计实际÷同期目标 | 月 | % |
| 预测年排放 | 已发生实绩+剩余月份预测 | 日/月 | tCO₂（P50 及区间） |
| 配额缺口 | 预测/确认排放-可用配额-拟用抵销量 | 日/月 | tCO₂（正值为缺口） |
| 数据完整率 | 按期有效数据点÷应到数据点 | 日/月 | % |
| 异常关闭率 | 期内已关闭异常÷应处理异常 | 周/月 | % |
| 项目实绩减排 | 基准情景排放-报告期排放（经 MRV 调整） | 月/年 | tCO₂ |

## 6.6 AI 能力边界与治理

| 允许 | 禁止 |
|---|---|
| 将规则命中的事实组织成解释文本 | 虚构表计、账单、因子、价格或政策 |
| 从审核过的措施库匹配候选措施 | 未经确认直接修改核算结果或锁定状态 |
| 基于显式假设进行节能与经济性试算 | 声称相关性即因果、保证节能收益 |
| 生成报告草稿、问题摘要和汇报提纲 | 替代第三方核查、正式评价或审批结论 |
| 记录引用数据、知识条目、模型版本 | 自动控制设备、自动交易或对外报送 |

**治理要求**：

- 每次 AI 输出保存输入数据范围、知识库版本、模型版本、提示模板版本和用户反馈。
- 对低置信度、数据缺失或超出措施库覆盖的情况，系统应明确说"不足以判断"。
- 金额、减排量和回收期由确定性计算服务生成；大模型仅负责解释，不负责心算。
- 输出中不得包含学生个人信息；默认只使用建筑、设施和聚合运营数据。

## 6.7 数据质量管理设计

| 规则类型 | 示例 | 结果 |
|---|---|---|
| 完整性 | 应到 24 个小时点但仅 22 个；账单附件缺失 | 警告/阻断 |
| 格式与单位 | kWh/MWh 混用、负数、日期跨期 | 阻断 |
| 合理性 | 单点超设备容量、日环比突增 50% | 告警 |
| 一致性 | 分表和≠总表；表计累计量与账单差异超阈值 | 待解释 |
| 时序与业务 | 寒暑假教学楼负荷未下降；夜间基载异常 | 告警 |
| 凭证有效性 | 绿电凭证量小于申报绿电量；校准证书到期 | 阻断/提醒 |

**质量管理机制**：

- 质量问题状态：待确认 → 已分派 → 处理中 → 待复核 → 已关闭/误报；所有状态留痕。
- 严重级别：阻断、严重、一般、提示；只有阻断问题会阻止周期锁定。
- 质量评分由完整性、及时性、合理性、一致性、可追溯性构成，权重后台配置。
- 异常检测先使用明确规则与统计阈值；Demo 中的"AI 识别"需标注为模拟推断。

# 7. 核心数据模型

## 7.1 实体关系

| 实体 | 关键字段 | 主要关系 |
|---|---|---|
| 组织/校区/建筑 | 编码、名称、类型、面积、人数、运营状态、有效期 | 建筑属于校区；关联设施、表计、责任人 |
| 设施/计量点 | 能源类型、倍率、精度、安装位置、上下级表、校准有效期 | 表计关联设施/建筑；形成计量树 |
| 原始读数/账单 | 期间、原值、单位、来源、接收时间、附件、版本 | 映射计量点；经校验形成活动数据 |
| 活动数据 | 期间、标准值、单位、质量状态、估算标志、复核状态 | 参与核算批次 |
| 排放因子 | 能源、数值、单位、来源、适用期、版本、审批状态 | 被计算明细引用 |
| 核算批次/明细 | 边界、期间、公式版本、输入快照、结果、锁定状态 | 汇总到报告版本 |
| 质量问题/工单 | 规则、对象、严重度、影响量、状态、责任人、证据 | 关联数据、异常、整改 |
| 措施/项目/MRV | 适用条件、基线、预算、里程碑、预计/实绩收益 | 由异常转项目，贡献目标 |
| 配额/资产流水 | 年度、类型、数量、价格、凭证、账户、状态 | 汇总余额和履约 |
| 评价项/材料 | 规则版本、得分、适用性、附件、整改任务 | 生成自评与材料包 |

## 7.2 数据一致性约束

- 所有页面使用同一套源数据和指标服务，禁止为每个页面单独写互相矛盾的数字。
- 总排放 = 各能源排放之和；校区和建筑汇总与学校总量一致，允许因未分摊公共项产生可解释差异。
- 异常影响量、建议节电量、减排量和配额缺口之间可复算。
- 所有模拟价格、因子、配额和目标均标注来源类型与"演示参数"。

## 7.3 数据存储要求

- 数据原始记录和管理台账等材料至少保存 5 年。
- 审计日志按人/时间/对象可追溯。
- 文件哈希、版本、有效期、下载审计。

## 10.1 风险矩阵

| 风险类型 | 风险描述 | 概率 | 影响 | 风险等级 | 应对措施 |
|---|---|---|---|---|---|
| 范围风险 | 三周周期内需求膨胀，破坏主流程质量 | 高 | 高 | 🔴 严重 | 冻结 P0 范围，P1 只做摘要/原型；变更走评审 |
| 数据风险 | 模拟数据不一致，跨页面数字矛盾 | 中 | 高 | 🟠 高 | 统一数据模型和指标服务；数据一致性自动化校验 |
| 技术风险 | 核算公式计算结果与政策口径不符 | 中 | 高 | 🟠 高 | 以现行标准为准，公式配置化；引入碳管理专家复核 |
| 技术风险 | 前端图表性能在大数据量下卡顿 | 低 | 中 | 🟡 中 | 分页加载、数据聚合；Demo 控制数据规模 |
| 业务风险 | AI 归因不准确，误导用户判断 | 中 | 中 | 🟡 中 | AI 输出标注"候选"和置信度；要求现场确认 |
| 业务风险 | 节能收益受天气、运维等影响，实际与预测偏差大 | 高 | 中 | 🟡 中 | 使用区间预测；MRV 复盘机制 |
| 合规风险 | 绿电凭证处理不符合当年政策 | 低 | 高 | 🟡 中 | 因子和凭证规则按年度配置；正式项目由碳专业人员确认 |
| 合规风险 | 虚拟高校信息影射真实学校 | 低 | 高 | 🟡 中 | 明确标注"虚拟客户，仅用于演示" |
| 业务风险 | 配额价格波动，Demo 展示伪实时价格 | 中 | 中 | 🟡 中 | 只做可调情景参数，不展示伪实时价 |
| 安全风险 | 演示数据泄露被误认为真实数据 | 低 | 中 | 🟢 低 | 全页面"Demo 模拟数据"水印；数据脱敏 |
| 依赖风险 | 政策/因子在开发期间更新 | 低 | 中 | 🟢 低 | 配置化设计，支持热更新 |

## 10.2 边界条件

### 业务边界

- 一期仅服务北京市重点碳排放高校，不覆盖医院和通用公共机构。
- 核算边界为法人边界内的固定设施，不含 Scope 3 和项目级碳足迹。
- 配额交易仅模拟方案，不连接真实交易系统。
- AI 输出为辅助建议，不替代人工审批、核算和核查。

### 技术边界

- Demo 使用模拟数据，不涉及真实设备协议和网关。
- "实时监测"在 Demo 中指小时/日级模拟数据展示近实时效果。
- 并发能力仅保证演示场景（≥ 20 用户），不保证生产级高可用。

### 数据边界

- 所有排放因子、配额、价格及政策期限按年度配置，禁止硬编码。
- 所有模拟参数标注"演示参数"来源。
- 预测值必须与实绩分开标注，不得混同。
